## 上下文工程概述

### 什么是上下文工程？

**上下文工程（Context Engineering）** 是设计、优化和管理大语言模型（LLM）输入上下文的系统化方法，目标是提高模型输出的质量、准确性和一致性。

```

│         上下文工程核心要素                │
├─────────────────────────────────────────┤
│ 1. Prompt 设计                          │
│    - 系统指令                           │
│    - 任务描述                           │
│    - Few-shot 示例                     │
│    - 约束条件                           │
│                                         │
│ 2. 上下文窗口管理                        │
│    - 长度控制                           │

│                                         │
│ 3. 历史对话管理                         │
│    - 对话记忆                           │
│    - 信息总结                           │
│    - 增量更新                           │
│                                         │
│ 4. Schema 和结构化信息                  │
```

## 评测与上下文工程的关系

### 为什么 DST 和 FnCTOD 评测对上下文工程重要？

这两个评测本质上是在测试：**你设计的上下文能否有效引导 LLM 完成特定任务**。

### DST 评测的意义

#### 1. 上下文设计质量评估

DST（Dialogue State Tracking）评测你的 prompt 能否让模型：
- 理解对话意图
- 提取关键槽位
- 维护对话状态

**实际意义：**
```python
# 你的 prompt 设计：
prompt = """
你是一个对话系统。请从用户输入中提取槽位信息。

用户说：我想订一个明天的标准间
请提取：{酒店类型, 日期, 房间类型}
"""

# DST 评测会告诉你：
# - 这个 prompt 的槽位准确率是多少？
# - 哪些槽位容易漏提或错提？
# - 如何改进 prompt 设计？
```

#### 2. 多轮对话上下文管理

测试你的上下文保留策略：
- 完整历史 vs 压缩历史
- 滑动窗口策略
- 对话总结方法

**案例对比：**
```
策略 A（完整历史）：
  上下文长度：2000 tokens
  联合准确率：85%

策略 B（智能总结）：
  上下文长度：800 tokens
  联合准确率：88% ✅

结论：策略 B 更优（更短+更准）
```

#### 3. 自由格式上下文的效果

评估开放式 prompt 的表现：
- 灵活性 vs 准确性的权衡
- 模型理解能力的边界
- 指令清晰度的重要性

### FnCTOD 评测的意义

#### 1. 结构化上下文设计

测试函数调用格式作为上下文的效果：

**对比：**
```
自由格式（DST）：
  "请提取槽位..."
  槽位准确率：75%

函数调用格式（FnCTOD）：
  function: book_hotel
  parameters:
    - hotel_name: string
    - check_in: date
  槽位准确率：85% ✅

结论：结构化上下文提高 10% 准确率
```

#### 2. 约束性 Prompt 评估

验证结构化 prompt 的准确性：
- Schema 作为约束的效果
- 类型系统的价值
- 格式控制的有效性

**实际应用：**
```python
# 你的 Schema 设计：
hotel_schema = {
    "function": "book_hotel",
    "parameters": {
        "hotel_name": {
            "type": "string",
            "description": "酒店名称",
            "required": True
        },
        "check_in_date": {
            "type": "date",
            "format": "YYYY-MM-DD",
            "required": True
        }
    }
}

# FnCTOD 评测告诉你：
# - 这个 Schema 设计是否清晰？
# - 参数描述是否充分？
# - 约束是否有效？
```

#### 3. 上下文复杂度管理

评估复杂 Schema 对性能的影响：
- Schema 详细程度的最优点
- 参数数量对准确性的影响
- 嵌套结构的处理能力

### 场景 1: Prompt 模板优化

**目标**：找到最优的 prompt 模板

**方法：**

**优化示例：**
```
版本 A（低效）：
"提取对话中的信息"
→ 太模糊，准确率低

版本 B（改进）：
"提取以下槽位：酒店名称、入住日期、退房日期"

"根据以下 Schema 提取槽位：
- hotel_name (必需): 酒店名称
- check_in (必需): 入住日期 YYYY-MM-DD
- check_out (可选): 退房日期 YYYY-MM-DD"
→ 最详细，准确率最高
```

## 上下文工程最佳实践

### 基于评测结果的建议

#### 1. 优先使用结构化上下文

**证据**：FnCTOD 平均性能优于 DST 10-15%

**建议：**
- ✅ 使用函数调用格式
- ✅ 预定义清晰的 Schema
- ✅ 提供参数类型和约束

**反模式：**
- ❌ 完全自由格式的 prompt
- ❌ 模糊的任务描述
- ❌ 缺少结构化约束

#### 2. 平衡上下文详细度

**原则**：详细但不冗余

**最优实践：**
```python
# ✅ 好的设计
{
    "hotel_name": {
        "type": "string",
        "description": "酒店名称",
        "example": "希尔顿酒店"
    }
}

# ❌ 过于简单
{
    "hotel_name": "string"
}

# ❌ 过于详细
{
    "hotel_name": {
        "type": "string",
        "description": "用户想要预订的酒店的完整名称，可以包括品牌、位置等信息，应该是一个非空字符串，长度通常在 2-50 个字符之间...",
        # ... 更多冗余信息
    }
}
```

#### 3. 分层上下文设计

**推荐结构：**
```
┌─────────────────────────────────────┐
│ 1. 系统角色定义（System Role）       │
│    "你是一个酒店预订助手..."          │
├─────────────────────────────────────┤
│ 2. 任务描述（Task Description）      │
│    "你的任务是提取用户的预订信息..."  │
├─────────────────────────────────────┤
│ 3. Schema 定义（Schema）             │
│    function: book_hotel             │
│    parameters: ...                  │
├─────────────────────────────────────┤
│ 4. 示例对话（Examples）              │
│    User: "我想订个房间"              │
│    Assistant: {...}                 │
├─────────────────────────────────────┤
│ 5. 历史对话（History）               │
│    [最近 3 轮对话]                   │
├─────────────────────────────────────┤
│ 6. 当前输入（Current Input）         │
│    User: "明天入住"                  │
└─────────────────────────────────────┘
```

#### 4. 迭代优化流程

**标准流程：**
```
1. 设计初版上下文
   ↓
2. 运行评测获取基线
   ↓
3. 分析低性能区域
   ↓
4. 调整上下文策略
   ↓
5. 重新评测验证
   ↓
6. 重复步骤 3-5
```

**实际案例：**
```
迭代 1：基础 prompt
  F1 = 70%

迭代 2：添加 Schema
  F1 = 78% (+8%)

迭代 3：优化参数描述
  F1 = 83% (+5%)

迭代 4：添加示例
  F1 = 87% (+4%)

迭代 5：精简冗余信息
  F1 = 89% (+2%)

总提升：19%
```

## 评测指标的指导意义

### 指标与上下文优化的对应关系

| 评测指标 | 对上下文工程的意义 | 优化方向 |
|---------|------------------|---------|
| **槽位准确率** | 上下文是否清晰传达了需要提取的信息 | - 明确槽位定义<br>- 提供清晰示例<br>- 减少歧义 |
| **联合准确率（严格）** | 上下文是否支持完整任务理解 | - 强化整体任务描述<br>- 明确必需 vs 可选<br>- 提供完整示例 |
| **联合准确率（软匹配）** | 上下文引导的完整性（允许额外信息） | - 平衡宽松和严格<br>- 评估过度提取 |
| **精确率** | 上下文是否有效避免误提取 | - 加强约束条件<br>- 明确排除项<br>- 提供负例 |
| **召回率** | 上下文是否充分引导信息提取 | - 补充提示信息<br>- 强调重要槽位<br>- 增加覆盖面 |
| **F1 分数** | 上下文设计的综合平衡效果 | - 综合优化<br>- 平衡精确和召回 |

### 诊断模式

#### 低槽位准确率 → 槽位定义不清

**症状：**
```
槽位准确率: 60%
精确率: 65%
召回率: 70%
```

**诊断：**
- 模型不理解什么是需要提取的槽位

**解决方案：**
```python
# 改进前
prompt = "提取酒店信息"

# 改进后
prompt = """
请提取以下槽位：
1. hotel_name: 酒店名称（如：希尔顿酒店）
2. check_in: 入住日期（格式：YYYY-MM-DD）
3. check_out: 退房日期（格式：YYYY-MM-DD）
"""
```

#### 低联合准确率 → 整体理解不足

**症状：**
```
槽位准确率: 85%
联合准确率: 60%  ← 差距大
```

**诊断：**
- 个别槽位准确，但整体任务理解不完整

**解决方案：**
```python
# 添加整体任务描述
prompt = """
任务：提取完整的酒店预订信息

必需信息：
- 酒店名称
- 入住日期
- 退房日期

可选信息：
- 房间类型
- 客人数量
"""
```

#### 低召回率 → 提示不足

**症状：**
```
精确率: 90%
召回率: 65%  ← 低
```

**诊断：**
- 模型提取的内容准确，但漏提很多

**解决方案：**
```python
# 添加提示
prompt += """
注意：
- 仔细检查每一轮对话
- 不要遗漏任何提到的信息
- 隐含信息也要提取（如"明天"应转换为具体日期）
"""
```

#### 低精确率 → 约束不够

**症状：**
```
精确率: 65%  ← 低
召回率: 90%
```

**诊断：**
- 模型过度提取，包含了不该提取的信息

**解决方案：**
```python
# 加强约束
prompt += """
约束：
- 只提取明确提到的信息
- 不要猜测或推断
- 不确定的信息标记为 null
- 严格遵守数据格式
"""
```

## 常见问题解答

### Q1: 应该选择 DST 还是 FnCTOD 进行上下文优化？

**A:** 取决于你的应用场景：

**选择 FnCTOD 如果：**
- ✅ 你有明确的业务 Schema
- ✅ 需要严格的格式控制
- ✅ 槽位类型和取值范围已知
- ✅ 追求更高的准确性

**选择 DST 如果：**
- ✅ Schema 未定或经常变化
- ✅ 需要灵活处理未知槽位
- ✅ 探索性任务
- ✅ 更关注模型的理解能力

**最佳实践：**
```
1. 先用 DST 探索和验证
2. 确定 Schema 后用 FnCTOD 优化
3. 定期用两者对比验证
```

### Q2: 如何根据评测结果优化上下文设计？

**A:** 遵循系统化的优化流程：

**步骤 1: 建立基线**
```bash
python benchmark/run_fnctod_transfertod.py --limit 100
# 基线：F1 = 75%
```

**步骤 2: 识别问题**
```
分析指标：
- 槽位准确率低 → 槽位定义问题
- 召回率低 → 提示不足
- 精确率低 → 约束不够
```

**步骤 3: 针对性改进**
```python
# 例如：召回率低（65%）
# 改进：添加提示
prompt += "注意提取所有提到的信息，包括隐含信息"
```

**步骤 4: 验证改进**
```bash
python benchmark/run_fnctod_transfertod.py --limit 100
# 新结果：F1 = 82% (+7%)
```

**步骤 5: 迭代优化**
```
重复步骤 2-4，直到达到目标性能
```

### Q3: 评测结果如何应用到实际生产环境？

**A:** 遵循以下最佳实践：

**1. 评测环境尽量接近生产环境**
```python
# 使用生产环境的配置

```
