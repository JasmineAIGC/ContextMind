# RiSAWOZ DST评测指标改进指南

## 问题概述

用户在100条对话上测试，结果很差：

```
【整体汇总统计】
总测试对话数: 100
平均槽位准确率 (Slot Accuracy): 48.56%
平均联合准确率-严格 (Joint Accuracy Strict): 0.00%  ← 最严重！
平均联合准确率-软匹配 (Joint Accuracy Soft): 15.00%
平均精确率 (Precision): 23.26%  ← 很低！
平均召回率 (Recall): 51.14%
平均F1分数 (F1 Score): 30.79%
平均轮次意图准确率 (Turn Intent Accuracy): 40.78%
```

### 关键问题

1. **Joint Accuracy Strict = 0.00%**: 100个对话中没有一个得到所有槽位都正确
2. **Precision = 23.26%**: 大量误提取（false positives）
3. **Domain-specific差异**:
   - 餐厅: 最差（33.55% slot accuracy, 16.34% precision）
   - 酒店: 中等（63.29% slot accuracy, 29.15% precision）
   - 旅游景点: 中等（52.75% slot accuracy, 25.72% precision）

## 根本原因分析

### 原因1: 槽位键名称不匹配

**问题**: LLM使用自然变体，不完全匹配本体定义

**示例**:
```python
# 旅游景点领域
期望: {'旅游景点-区域': '苏州', '旅游景点-特点': '风景优美'}
LLM提取: {'旅游景点-位置': '苏州', '旅游景点-特色': '风景优美'}
          ↑ 应该是"区域"          ↑ 应该是"特点"
匹配结果: 0/2 ❌

# 餐厅领域
期望: {'餐厅-区域': '市中心', '餐厅-人均消费': '100元'}
LLM提取: {'餐厅-地址': '市中心', '餐厅-价格': '100元'}
匹配结果: 0/2 ❌
```

**影响**:
- 即使信息正确，键名不匹配导致0%准确率
- 这是Joint Accuracy = 0%的主要原因

### 原因2: 'intent'字段被当作槽位

**问题**: LLM返回的'intent'字段被包含在槽位比较中

**示例**:
```python
期望: {'旅游景点-名称': '拙政园'}
LLM提取: {'旅游景点-名称': '拙政园', 'intent': 'Inform'}
         ↑ 正确的槽位             ↑ 不应该算作槽位
         
比较时: 期望有1个槽位，提取到2个槽位
结果: Precision降低（false positive）
```

**影响**:
- 每个turn都会额外有一个'intent'，导致precision下降
- Joint Accuracy计算时会认为槽位数量不匹配

### 原因3: 值的标准化不够充分

**问题**: 虽然有normalization，但还不够

**示例**:
```python
期望: '金鸡湖 景区'（有空格）
提取: '金鸡湖景区'（无空格）
当前normalization: 移除了空格，应该匹配
但可能还有其他格式差异未处理
```

## 解决方案

### 改进1: 槽位名称映射 ✅

**实施位置**: `contextmind/modes/dst/response_parser.py`

**核心思路**: 将LLM的自然变体自动映射到标准槽位名

**实现**:
```python
SLOT_NAME_MAPPING = {
    # 旅游景点领域 (10个映射)
    '旅游景点-特色': '旅游景点-特点',
    '旅游景点-特征': '旅游景点-特点',
    '旅游景点-位置': '旅游景点-区域',
    '旅游景点-地点': '旅游景点-区域',
    '旅游景点-地址': '旅游景点-区域',
    '旅游景点-景点名称': '旅游景点-名称',
    '旅游景点-景区名称': '旅游景点-名称',
    '旅游景点-价格': '旅游景点-消费',
    '旅游景点-费用': '旅游景点-消费',
    '旅游景点-人群': '旅游景点-最适合人群',
    
    # 酒店领域 (8个映射)
    '酒店-位置': '酒店-区域',
    '酒店-地点': '酒店-区域',
    '酒店-地址': '酒店-区域',
    '酒店-酒店名称': '酒店-名称',
    '酒店-费用': '酒店-价格',
    '酒店-房型': '酒店-房型',
    '酒店-星级': '酒店-星级',
    '酒店-评分': '酒店-评分',
    
    # 餐厅领域 (8个映射)
    '餐厅-位置': '餐厅-区域',
    '餐厅-地点': '餐厅-区域',
    '餐厅-地址': '餐厅-区域',
    '餐厅-餐厅名称': '餐厅-名称',
    '餐厅-菜品': '餐厅-菜系',
    '餐厅-价格': '餐厅-人均消费',
    '餐厅-费用': '餐厅-人均消费',
    '餐厅-人均': '餐厅-人均消费',
}

def _filter_if_needed(self, updates):
    # 自动应用映射
    if self.enable_slot_mapping:
        mapped_updates = {}
        for slot, value in updates.items():
            if slot in SLOT_NAME_MAPPING:
                mapped_slot = SLOT_NAME_MAPPING[slot]
                logger.debug(f"槽位名称映射: {slot} -> {mapped_slot}")
                mapped_updates[mapped_slot] = value
            else:
                mapped_updates[slot] = value
        updates = mapped_updates
    
    # 移除'intent'字段
    filtered = {k: v for k, v in updates.items() if k != 'intent'}
    return filtered
```

```python
LLM: {'旅游景点-位置': '苏州', '旅游景点-特色': '风景优美', 'intent': 'Inform'}
匹配: 0/2 ❌

# After (自动映射)
期望: {'旅游景点-区域': '苏州', '旅游景点-特点': '风景优美'}
映射后: {'旅游景点-区域': '苏州', '旅游景点-特点': '风景优美'}
        ↑ 从'位置'映射           ↑ 从'特色'映射，'intent'已移除
匹配: 2/2 ✓
```

### 改进2: 过滤'intent'字段 ✅

**问题**: 'intent'不是真正的槽位，但被计入了

**效果**:

## 技术要点

### 1. 槽位名称映射的原理

**为什么需要**:
- LLM是语言模型，会使用最自然的表达
- "位置"比"区域"更自然，"特色"比"特点"更常用
- 不能期望LLM完全遵循本体定义

**如何工作**:
- 预定义常见变体到标准名称的映射
- 在解析阶段自动应用映射
- 对用户透明，不需要修改评测代码

**可扩展性**:
- 新增映射: 只需在`SLOT_NAME_MAPPING`中添加
- 支持多对一映射（多个变体 → 一个标准名）
- 可以针对不同domain定制

### 2. 'intent'字段的处理

**为什么要移除**:
- 'intent'是元信息，不是对话状态的一部分
- 包含在槽位中会影响:
  - Precision计算（算作false positive）
  - Joint Accuracy（槽位数量不匹配）

**何时移除**:
- 在`_filter_if_needed()`中，槽位映射之后
- 确保所有后续处理都不会看到'intent'字段

### 3. 性能优化建议

**如果指标仍然不理想**:

1. **检查日志**: 看哪些槽位未被映射
   ```bash
   grep "槽位名称映射" logs/*.log
   ```

2. **增加映射**: 在`SLOT_NAME_MAPPING`中添加新发现的变体

3. **调整Prompt**: 在prompt中明确列出标准槽位名称

4. **使用语义匹配**: 启用`--use-semantic-match`提高值匹配
